# Портал ELVLift: автоматизации простым языком

## Что это за документ

Это человекочитаемая расшифровка найденных CRM-автоматизаций портала `b24.elvlift.ru`.
Документ основан на:

- фактической выгрузке шаблонов из `bizproc.workflow.template.list`
- нормализованном отчёте из `normalized/bitrix24_automation_report.json`
- официальной терминологии Bitrix24 из документации:
  - [Workflows and Automation Rules](https://apidocs.bitrix24.com/api-reference/bizproc/index.html)
  - [Business Process Templates: Overview of Methods](https://apidocs.bitrix24.com/api-reference/bizproc/template/index.html)

## Как читать этот документ

По официальной модели Bitrix24:

- шаблон бизнес-процесса всегда привязан к базовой сущности CRM
- запуск может быть автоматическим или ручным
- автоматизация может менять поля, создавать связанные сущности, запускать другой шаблон, отправлять уведомления или письма

Ниже я разделяю:

- `Факт` — то, что явно видно в выгрузке шаблона
- `Интерпретация` — наиболее вероятное бизнес-объяснение логики
- `Риск / замечание` — места, где настройка выглядит спорной, неполной или потенциально опасной

## Общая картина портала

На портале найдены 11 CRM-сущностей, но реальные шаблоны автоматизаций привязаны только к 5 из них:

- `Сделки`
- `Компании`
- `Договор`
- `Объект`
- `Лифт`

На уровне CRM есть несколько воронок сделок:

- `Коммерческая воронка`
- `Тендерная продажа`
- `Продажа по ФЗ`
- `Долгосрочная`

Но по публичному REST не удалось восстановить отдельные “роботы на стадиях” как явную карту `стадия -> робот`.
Это значит, что в текущей выгрузке портал выглядит не как система с большим количеством stage-роботов, а скорее как набор бизнес-процессов, запускаемых на создании, обновлении или вручную из карточек.

## Главный бизнес-сценарий портала

Самая содержательная цепочка автоматизации выглядит так:

1. В сущности `Объект` срабатывает шаблон `Создание лифтов`.
2. Шаблон создаёт один или несколько элементов в смарт-процессе `Лифт`.
3. Для каждого созданного лифта запускается ручной шаблон сделки `Прикрепить лифт`.
4. В сделке обновляется мультиполе со связанными лифтами.
5. Отдельный шаблон `Прикрепление объекта` может связывать сделку и объект в обратную сторону.

Проще говоря, портал автоматизирует связку:

`Сделка -> Объект -> Лифт`

Это и есть центральная ось найденной логики.

## Автоматизации по сущностям

### 1. Компании

#### Шаблон `[76] Заведение ИНН`

`Факт`

- Запуск: автоматически при создании компании
- Действие: `CrmChangeRequisiteActivity`
- В реквизиты записывается `RQ_INN`
- Источник значения: поле документа `UF_CRM_1760640732106`

`Интерпретация`

При создании компании система пытается взять ИНН из пользовательского поля карточки и записать его в реквизиты CRM.

`Риск / замечание`

- Внутри действия указано `CrmEntityType = CONTACT`, хотя шаблон привязан к `Компании`.
- Это выглядит нетипично и требует ручной проверки в интерфейсе:
  - либо процесс намеренно работает с контактными реквизитами
  - либо настройка сделана с ошибкой

#### Шаблон `[156] Рассылка писем`

`Факт`

- Запуск: вручную из карточки компании
- Действие: `MailActivity`
- Тема письма берётся из `Parameter1`
- Текст письма берётся из `Parameter2`
- Отправитель формируется через `ASSIGNED_BY_ID`
- Получатель зашит явно: `i@egor-tsygankov.ru`

`Интерпретация`

Это ручной шаблон для отправки письма из карточки компании с вводом темы и текста.

`Риск / замечание`

- Получатель жёстко захардкожен.
- Если это боевая логика, она завязана не на данные компании, а на один конкретный email.
- Такой шаблон больше похож на персональный служебный инструмент, чем на универсальную автоматизацию.

### 2. Объект

#### Шаблон `[77] Создание лифтов`

`Факт`

- Запуск: автоматически при создании или обновлении объекта
- Есть шаги:
  - изменение переменной
  - несколько условий
  - изменение документа
  - цикл `While`
  - создание элемента `Лифт` через `CrmCreateDynamicActivity`
  - запуск дочернего шаблона `79`
  - возможное прерывание процесса
- Создаваемая сущность: смарт-процесс `Лифт` (`DynamicTypeId = 1046`)
- При создании лифта заполняются связи:
  - ответственный
  - компания
  - родительская сделка
  - родительский договор
  - текущий объект
- После создания лифта запускается шаблон `79` для сделки

`Интерпретация`

Это основной производственный шаблон портала.
Он, вероятнее всего, читает из объекта количество или состав будущих лифтов, затем в цикле создаёт отдельные карточки `Лифт` и сразу привязывает каждую к сделке, договору и объекту.

`Что это значит для бизнеса`

Если менеджер или инженер заполняет карточку объекта, портал может автоматически разложить объект на набор дочерних сущностей `Лифт`, чтобы дальше вести их отдельно.

`Риск / замечание`

- Логика явно сложнее остальных шаблонов и зависит от пользовательских полей, названия которых в REST пришли только как технические коды.
- Есть служебный маркер `UF_CRM_6_1760649816665`, который процесс выставляет в документе.
- Без расшифровки пользовательских полей через UI невозможно на 100% сказать, что именно является входным триггером цикла.

### 3. Лифт

#### Шаблон `[78] Добавление в сделку`

`Факт`

- Запуск: автоматически при создании элемента `Лифт`
- В выгрузке шаблон существует, но внутри не видно содержательных действий кроме корневого контейнера

`Интерпретация`

Либо это пустой шаблон-заготовка, либо его фактическая логика была удалена/отключена, либо в REST не раскрылась полезная часть структуры.

`Риск / замечание`

- На текущий момент на этот шаблон нельзя опираться как на рабочий бизнес-сценарий.

### 4. Сделки

#### Шаблон `[79] Прикрепить лифт`

`Факт`

- Запуск: вручную
- Параметр запуска: `Parameter1`
- Единственное действие: `SetFieldActivity`
- В мультиполе `UF_CRM_1760618188` добавляется значение `Parameter1`
- Режим `MergeMultipleFields = Y`

`Интерпретация`

Шаблон нужен для добавления ID лифта в список связанных лифтов сделки.
Именно его вызывает шаблон `Создание лифтов` после создания каждого нового лифта.

`Что это значит для бизнеса`

Сделка накапливает перечень лифтов, связанных с проектом.

#### Шаблон `[80] Прикрепление объекта`

`Факт`

- Запуск: автоматически при обновлении сделки
- Используется `ForEachActivity` по полю `UF_CRM_1760618213`
- Для каждого значения выполняется `CrmUpdateDynamicActivity`
- Обновляется смарт-процесс `Объект` (`DynamicTypeId = 1050`)
- В объект записывается `PARENT_ID_2 = ID сделки`

`Интерпретация`

Когда в сделке заполнен список объектов, шаблон проходит по нему и в каждой карточке объекта проставляет ссылку на текущую сделку.

`Что это значит для бизнеса`

Связь `сделка <-> объект` поддерживается автоматически, чтобы объект “знал”, к какой сделке он относится.

#### Шаблон `[107] Постановака ответственного`

`Факт`

- Запуск: вручную
- Выбирается сотрудник через `GetUserActivity`
- Источник параметра выбора: поле сделки `COMMENTS`
- Затем отправляется `IMNotifyActivity`
- Шаг `CrmChangeResponsibleActivity` присутствует, но в выгрузке он неактивен
- Уведомление отправляется от `user_1` к `user_1`

`Интерпретация`

Шаблон выглядит как незавершённая или частично отключённая попытка автоматизировать назначение ответственного.
Сейчас он больше похож на выбор кандидата и отправку уведомления, чем на реальную смену ответственного.

`Риск / замечание`

- Реальная смена ответственного, вероятно, не выполняется.
- Уведомление завязано на `user_1`, что похоже на техническую или тестовую настройку.
- Название шаблона содержит опечатку, что дополнительно указывает на невылизанную конфигурацию.

### 5. Договор

#### Шаблон `[82] Привязка компаний и контактов`

`Факт`

- Запуск: вручную
- Два раза вызывается `CrmGetDynamicInfoActivity` для сущности типа `4`
- Поиск идёт по названию компании в двух полях договора
- Затем в договор записываются:
  - `COMPANY_ID`
  - `MYCOMPANY_ID`

`Интерпретация`

Шаблон вручную ищет две компании по названиям, указанным в договоре, и ставит их как:

- компания клиента
- ваша компания / юрлицо

`Что это значит для бизнеса`

Это сервисный шаблон для довязки карточки договора к правильным юридическим лицам, если они ещё не были проставлены напрямую.

## Что на портале не найдено

В выгрузке не нашлось явных автоматизаций для:

- лидов
- предложений
- смарт-счетов
- стадий воронок сделок как отдельных роботов
- большинства найденных смарт-процессов

Это не означает, что в интерфейсе вообще нет роботов.
Это означает более узкую вещь:

- через доступный REST и текущий вебхук не удалось получить отдельную полную карту stage-роботов
- зато удалось получить карту шаблонов бизнес-процессов, привязанных к CRM-сущностям

## Практический вывод для человека, который будет разбираться в портале

Если объяснять совсем просто, то автоматизации портала сейчас выглядят так:

- при работе с `Объектом` система умеет автоматически создавать связанные записи `Лифт`
- затем эти лифты автоматически или полуавтоматически привязываются к `Сделке`
- отдельно есть служебные ручные процессы для:
  - заполнения ИНН/реквизитов
  - привязки объекта к сделке
  - привязки компаний к договору
  - рассылки писем
  - выбора/уведомления ответственного

То есть портал больше похож на CRM с кастомной логикой вокруг структуры проекта `Сделка -> Объект -> Лифт`, чем на CRM, где вся логика сидит в роботах по стадиям.

## Что я бы проверил следующим шагом

1. Открыть в UI шаблон `[77] Создание лифтов` и расшифровать пользовательские поля:
   - `UF_CRM_6_1760643248`
   - `UF_CRM_6_1760649816665`
2. Проверить, почему `[76] Заведение ИНН` меняет реквизиты с `CrmEntityType = CONTACT`, хотя шаблон висит на компании.
3. Проверить, нужен ли вообще шаблон `[78] Добавление в сделку`, потому что сейчас он выглядит пустым.
4. Проверить `[107] Постановака ответственного`:
   - почему шаг смены ответственного неактивен
   - зачем уведомление уходит на `user_1`
5. Проверить `[156] Рассылка писем`, потому что получатель там захардкожен.
6. Если задача всё же именно в stage-роботах сделок, дополнительно пройтись по UI воронок вручную:
   - `CRM -> Сделки -> Роботы`
   - потому что REST-карта по стадиям в данном кейсе не раскрылась
