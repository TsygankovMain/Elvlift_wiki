# План работ по «Проверке системы» портала b24.elvlift.ru

**Основание:** запись экрана «Проверки системы» (Настройки → Инструменты → Проверка системы, вкладка «Работа портала») от 25.09.2026 15:07 МСК, 37 шагов. Платформа — «1С-Битрикс24» 26.400.0. Снаружи 25.09 в 15:10 МСК дополнительно проверены сертификат, DNS и порты.

## Коротко

На вкладке «Работа портала» пять красных пунктов и шесть замечаний. Большинство из них — следствие **одной** поломки: портал не может подключиться сам к себе («Работа с сокетами»). Три теста так и пишут: «не удалось проверить из-за ошибки в работе с сокетами».

Корень тот же, что уже есть в отчётах 22.09 и 25.09. **По адресу `http://b24.elvlift.ru` отвечает не портал, а страница входа в роутер MikroTik.** Из-за этого:

- Let's Encrypt не может продлить сертификат: проверочный адрес `/.well-known/acme-challenge/` отдаёт 404 от роутера. Сертификат просрочен с 09.09.2026 — уже 16 дней;
- портал, обращаясь к себе, попадает в роутер или спотыкается о просроченный сертификат, и тест сокетов падает. За ним по цепочке не проходят Диск, WebDAV и оценка производительности.

**Первый шаг делает сетевой администратор клиента** — перенастроить роутер. Без этого остальное чинить бессмысленно.

Отдельная, независимая беда — **с портала не уходит почта** (ошибка в тесте «Отправка почтовых уведомлений»). Это задевает уже сделанный пункт 9 «Скорой помощи»: письма о просроченных задачах и делах включены, но, скорее всего, не доходят.

## Итоги диагностики 25.09 (скрипт в «Командной PHP-строке»)

Сервер — «Виртуальная машина 1С-Битрикс» (BitrixVM) на Linux el9, PHP 8.5.4, внутренний адрес 172.16.101.12. Сертификаты выпускает штатный dehydrated.

**Проблем оказалось две, а не пять:**

1. **Просроченный сертификат ломает всё красное, кроме почты.** Изнутри сети `b24.elvlift.ru` указывает прямо на сервер (172.16.101.12). По http портал достаёт сам себя без проблем, все порты открыты, NAT и `/etc/hosts` ни при чём. Не проходит только https: `operation failed`, проверка сертификата. Тест «Работа с сокетами» идёт по https, падает на просроченном сертификате и тянет за собой Диск, WebDAV и производительность. **Продлим сертификат — они позеленеют сами.**
2. **Почта не настроена.** PHP отправляет через `msmtp -t -i`, но у msmtp нет конфигурации: нет ни `/etc/msmtprc`, ни `/home/bitrix/.msmtprc`. Каждое письмо портала уходит в никуда. Чинится из админки: файл в домашней папке bitrix доступен на запись.

Остальное:

- **Push работает через облачный сервер Битрикс** (`server_mode = shared`, rtc-cloud.bitrix24.tech), свой Push-сервер не нужен. Замечание про мобильное приложение, скорее всего, тоже из-за сертификата — проверим после продления. В настройках остался адрес 172.16.30.5:8895, похоже, от прежнего сервера. В облачном режиме он не используется.
- **Быстрая отдача файлов Диска уже включена** (`bx_fast_download = Y`) — делать нечего.
- **Сертификат из админки не продлить:** файлы принадлежат root, Let's Encrypt проверяет домен через порт 80, а снаружи он ведёт на MikroTik. Гипотеза для админа клиента: проброс 80 раньше шёл на 172.16.30.5, прежний адрес сервера, и после переезда на 172.16.101.12 его не перенастроили.

## План работ

### Этап 0. Подготовка — Мейнсофт + клиент

1. Получить доступ к серверу портала по SSH (сейчас его у нас нет, есть только администратор портала) и узнать, как устроен сервер: «Виртуальная машина 1С-Битрикс» (BitrixVM) или ручная сборка. От этого зависят способы в этапах 2 и 4.
2. Согласовать окно работ в нерабочее время. Совместить его с установкой обновлений из отчёта 25.09, чтобы не останавливать портал дважды.
3. Сделать резервную копию портала и конфигов веб-сервера перед любыми правками.

### Этап 1. Роутер — сетевой администратор клиента (блокер)

1. Закрыть вход в веб-интерфейс MikroTik из интернета.
2. Пробросить порт 80 внешнего адреса 88.84.193.150 на сервер портала, как уже проброшен 443.
3. Проверка: `http://b24.elvlift.ru` открывает портал (или перенаправляет на https), а не роутер.

### Этап 2. Сертификат — Мейнсофт

1. Выпустить сертификат Let's Encrypt заново: в BitrixVM — через меню виртуальной машины, иначе — через certbot.
2. Проверить и починить автопродление: по какой причине оно не сработало, есть ли задание по расписанию.
3. Проверка: в браузере нет предупреждения, срок — плюс 90 дней; REST и мобильное приложение подключаются без ошибок TLS.

### Этап 3. Портал видит сам себя — Мейнсофт

1. Перезапустить «Проверку системы». Если тест сокетов проходит — сразу к этапу 4.
2. Если нет — сервер не может выйти на свой внешний адрес через роутер (NAT loopback). Два варианта: прописать `b24.elvlift.ru` на внутренний адрес сервера в `/etc/hosts` или включить hairpin NAT на MikroTik (второе делает админ клиента).
3. Прочитать «журнал проверки системы» — там точная причина отказа.

### Этап 4. Почта с портала — Мейнсофт + клиент

1. Клиент заводит в Яндекс 360 служебный ящик, например `noreply@elvlift.ru`, и пароль приложения к нему.
2. Мы настраиваем отправку через SMTP Яндекса: в BitrixVM — пункт меню настройки почты сайта (msmtp), иначе — msmtp вручную или SMTP в настройках ядра. Отправитель по умолчанию в главном модуле — этот ящик.
3. Проверка: тест «Отправка почтовых уведомлений» зелёный; тестовое письмо о просроченной задаче пришло сотруднику. Проверить, что письма не попадают в спам: SPF уже разрешает Яндекс.

### Этап 5. Мгновенные сообщения в мобильном — Мейнсофт + клиент

1. Посмотреть в настройках модуля Push and Pull, какой адрес и порт отдаётся клиентам для чтения сообщений.
2. Лучше всего пустить Push через тот же 443 (путь `/bitrix/subws/` в nginx) — тогда роутер трогать не нужно. Если это невозможно — админ клиента пробрасывает нужный порт.
3. Проверка: тест «Мобильное приложение» зелёный; сообщение из чата мгновенно приходит в мобильный.

### Этап 6. Перепроверка и хвосты — Мейнсофт

1. Прогнать «Проверку системы» полностью, включая вкладку «Тестирование конфигурации», которая в записи не запускалась.
2. Разобрать то, что проявится после починки сокетов:
   - Диск — включить быструю отдачу файлов через nginx в настройках главного модуля;
   - WebDAV для MS Office — проверить, что веб-сервер пропускает запросы WebDAV в PHP;
   - оценка производительности — записать результат (эталон BitrixVM ≈ 30 единиц) и сравнить под нагрузкой.
3. Короткий отчёт клиенту «было → стало» с новыми скриншотами проверки.

### Не делаем без отдельной просьбы

- **Соцсервисы** — не используются.
- **NTLM** — вход без пароля под учёткой Windows. Нужен только при домене и желании клиента, это отдельная настройка сервера.
- **MX для `b24.elvlift.ru`** — нужен только для писем в живую ленту от людей без учётки на портале.

## Что делаем из админки портала, без SSH

У нас есть учётка администратора. В админке есть «Командная PHP-строка» и «SQL запрос» (Настройки → Инструменты). Через них часть работ делается без доступа к серверу. Настройки меняем через API модулей (`Option::set`), а не прямым `UPDATE b_option`: так сбрасывается кэш настроек. SQL оставляем для чтения.

| Работа | Из админки? | Как |
|---|---|---|
| Диагностика сервера, сокетов, сертификата, почты, Push | ✅ | Скрипт [`scripts/diag-site-checker.php`](scripts/diag-site-checker.php) в «Командной PHP-строке», только чтение. **Первый шаг — до всех остальных** |
| Почта с портала | ✅ | SMTP средствами портала: `smtp.enabled` в `.settings.php` и SMTP Яндекса для отправителя. Нужен только служебный ящик от клиента |
| Push для мобильного через 443 | ✅, если nginx уже проксирует `/bitrix/subws/` (в BitrixVM — да) | Адреса слушателя в настройках модуля Push and Pull |
| Диск: быстрая отдача файлов | ✅ | Опция «Быстрая отдача файлов через nginx» в главном модуле |
| Обновления платформы | ✅ | «Обновление платформы» в админке, после резервной копии |
| Резервная копия | ✅ | «Резервное копирование» в админке; важно, куда она ляжет: хватит ли места на диске |
| Сертификат | ❌ | Нужен root на сервере и порт 80 на портал (этап 1). Единственный обход без роутера — DNS-проверка Let's Encrypt, нужен доступ к DNS `elvlift.ru` |
| Сокеты, если причина в NAT | ❌ | `/etc/hosts` требует root; или hairpin NAT на роутере |
| Роутер (этап 1) | ❌ | Только сетевой администратор клиента |

Что это меняет: SSH нужен только для сертификата и, возможно, для `/etc/hosts`. Если клиент даст доступ к DNS, можно выпустить сертификат вообще без роутера. Этапы 4–6 делаем сами в админке, не дожидаясь клиента, кроме почтового ящика. Оценка почти не меняется, но работы начинаются сразу.

**Порядок:** диагностика скриптом → почта, Диск, Push из админки → сертификат после этапа 1 или через DNS → перепроверка.
